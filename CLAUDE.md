# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Everlog is a native Android fitness/workout-tracking app (package `com.everlog`). Despite the repo name (`everlog-kotlin-multiplatform`), there is no shared/iOS Kotlin Multiplatform code yet. The Android app is being split into Gradle modules under `android/` (`common/*`, and `data`, `feature` and `test-fixtures` modules per feature; see Modules below and `android/README.md`), but almost all code still lives in the application module `:android:app` and moves out screen by screen (TAS-468). Some leftover references to KMP exist (e.g. a link in `PULL_REQUEST_TEMPLATE.md`) but don't reflect the current module layout.

The app itself is a mixed Kotlin/Java codebase (`android/app/src/main/java`, ~284 `.kt` and ~115 `.java` files) built on an older stack: MVP, RxJava 1 (`rx.Observable`, not RxJava 2/3), and EventBus — see Architecture below before assuming modern Android patterns (coroutines, Flow, Compose) apply. New screens are the exception: they're Jetpack Compose with view-models (see Compose screens and the design system).

## Common commands

Run all commands from the repo root; the Gradle wrapper targets the `:android:app` module.

- Unit tests: `./gradlew testDebugUnitTest` (CI runs `./gradlew --no-daemon --continue testDebugUnitTest`)
- Single unit test class: `./gradlew testDebugUnitTest --tests "com.everlog.SomeTest"`
- Instrumented/E2E tests (needs a connected device or emulator): `./gradlew connectedAndroidTest`
- Build debug APK: `./gradlew :android:app:assembleDebug`
- Build release bundle + upload native symbols: `./gradlew :android:app:bundleRelease :android:app:uploadCrashlyticsSymbolFileRelease`
- Clean: `./gradlew clean`

There is no ktlint/detekt configured — the only lint is Android's built-in lint (bundled into the `bundleRelease`/`assembleRelease` tasks via `isMinifyEnabled`/proguard).

### Build setup

Shared build setup lives in convention plugins in the `gradle-plugins/conventions` composite build (included from `settings.gradle.kts`), as in newsfeed-kotlin-multiplatform. Modules apply them through the version catalog (`alias(libs.plugins.everlog.android.…)`): `android-base-plugin` (SDK levels, JVM toolchain, desugaring, parcelize), `android-module-plugin` (a library module with `common:test`), `android-compose-plugin`, `android-feature-plugin` and `android-data-plugin` (a feature's `feature` and `data` modules with the common modules they use), `android-firebase-plugin` (google-services, Crashlytics, Performance; app only) and `android-application-binary-plugin` (app module, target SDK, version code and name). Put setup every module needs in a plugin, not in a module's `build.gradle.kts`. `android/README.md` says which plugin each module type applies.

### Local secrets required to build

The build reads `android/app/secrets.properties` (gitignored) via `envSecret(key)` (`gradle-plugins/conventions`), and will throw a `GradleException` if a required key is missing. Locally you need at least:
- `E2E_TEST_USER_EMAIL`, `E2E_TEST_USER_PASSWORD` (debug build config fields, used by the `LoginActivityTest` instrumented E2E test)
- `KEYSTORE_RELEASE_PASSWORD`, `KEYSTORE_RELEASE_ALIAS`, `KEYSTORE_RELEASE_ALIAS_PASSWORD` (only needed for release signing)

You'll also need `android/app/src/debug/google-services.json` / `android/app/src/release/google-services.json` (Firebase config, gitignored) and debug/release keystores. On CI these are all materialized by `tools/secrets/secrets.sh` from GitHub Actions secrets — see that script for the exact list of files/env vars it produces.

### Querying analytics in BigQuery

There's no `bq`/`gcloud` CLI installed. Query the GA4 export (`everlog-prod.analytics_173607556.events_*`) and Crashlytics export (`everlog-prod.firebase_crashlytics`) with the local helper instead. It runs in Docker with a gitignored service-account key from `tools/bigquery/`:
- `./tools/bigquery/bq_query.sh bigquery-credentials-prod.json --query "SELECT ..."`, or pass a `.sql` file. Add `--output tools/bigquery/<name>.csv` to save results. CSVs there are gitignored because they contain user PII. `--dry-run` and `--max-gb N` limit the cost.
- The KPI dashboard (Roadmap metrics for real new users, the paid test read) is built by `tools/monitoring`: `./tools/monitoring/refresh.sh`, then publish `tools/monitoring/out/dashboard.html` to the artifact URL in `tools/monitoring/README.md`. Its SQL holds the canonical real-user filters (robots, sideloads, the owner's account); reuse them in ad hoc queries.

### Versioning

`versionCode`/`versionName` are computed from `tools/versioning/version.txt` and `version_code.txt`, not hand-bumped per build. See `tools/versioning/README.md` for the full scheme (`MmmPTSS` version code format, per-environment suffixes). `tools/versioning/version_code.sh <staging|nightly|master> [--release]` is what CI (and `compute-app-version` action) invokes; it also shells out to `git describe`/`git rev-list` to derive a commit-based sequence number.

**Watch the sequence wrap.** A nightly's last two digits are the commits since `master`'s latest reachable tag modulo 80, so the 80th commit wraps to `00` and Play rejects the nightly as lower than the ones already uploaded. Check `git rev-list --count $(git describe --tags --abbrev=0 origin/master)..origin/master` when opening or merging a PR, and from 65 tell the user how many are left and suggest a release (then the usual version bump) or raising `version_code.txt`. A tag alone doesn't help: it resets the count under the same base, so the next nightly is lower too. The tag counted is the last one in `master`'s history, which skips hotfix tags (they stay on their branch).

## CI/CD

Three workflows in `.github/workflows/`, all built from shared composite actions in `.github/actions/`:
- `staging-check.yml` — runs on pushes to `master` and PRs into `master` or a `hotfix-*` branch: unit tests, debug build, instrumented tests, and deploys the debug APK to Firebase App Distribution (`everlog-staging-testers` group).
- `nightly-check.yml` — cron daily (can also be run manually, but only on `master`): same checks plus a **release** build uploaded to the Play Store internal track, with Slack status reporting to `MONITORING_SLACK_URL`.
- `release-check.yml` — manual (`workflow_dispatch`, requires a changelog input, only on `master` or a `hotfix-*` branch): full release build deployed to the Play Store production track via `fastlane android deploy_play_release`, then tags the released commit with `tools/versioning/version.txt` and creates a GitHub release listing the PRs since the previous tag (`tools/versioning/release_notes.sh`). Bumping the version for the next release is still a manual PR. Hotfixes (patch releases) always go through a `hotfix-<version>` branch off the release tag, released from that branch and then merged back into `master`: see "Hotfixes" in `tools/versioning/README.md`.

Fastlane lanes (`fastlane/Fastfile`): `deploy_firebase`, `deploy_play_internal`, `deploy_play_release`. Changelogs are auto-generated from `git log` since the last tag.

## Architecture

### Modules

The Android app is split into Gradle modules under `android/`: `app`, `common/<name>`, and `data`, `feature` and `test-fixtures` modules per feature. Almost all code still lives in `:android:app` and moves out bit by bit, leaf modules first (TAS-468). **`android/README.md` is the reference** for the layout, what each module holds, which convention plugin each type applies, and how to add a module or move code; keep it up to date when the structure changes. The rules that matter most:
- **app → feature → data → common**, enforced by the convention plugins: a dependency that breaks a rule fails the build. A feature never depends on another feature (screens open each other through the app's `Navigator`), data may depend on other features' data but never on UI, and test support (`test-fixtures`, `common:test`, `common:compose-test`) is only for tests.
- **Code moves with its tests**, never ahead of them: a feature's tests go to its modules when its code does, and common modules hold only common code and its tests.
- **What a feature needs from the app** (services on the app's managers, other features' screens) goes through one `…Dependencies` interface per feature that the app implements and registers in `ELApplication`, e.g. `ExerciseFeatureDependencies`. It stands in for DI until after TAS-468; `android/README.md` explains it.
- **Moved code takes the module's namespace as its package**, except anything the system knows by its full class name (the launcher activity, services, receivers behind pending alarms and notification intents). R8 keep rules for what Firestore or Gson maps by reflection move to the module's `consumerProguardFiles`; check them with `./gradlew :android:app:minifyReleaseWithR8` and the mapping.

### Pattern: MVP + RxJava 1 + EventBus (not MVVM/coroutines)

- `BasePresenter` / `BaseMvpView` (`common:mvp`, with the base activity, fragments, bottom sheets and views, `DialogBuilder`'s generic prompts and EventBus) — every screen has a Presenter attached/detached with the view lifecycle (`attachView`/`detachView`). Presenters hold a `CompositeSubscription` for RxJava subscriptions and register themselves on the global `EventBus` (greenrobot) for cross-screen notifications (e.g. data store updates).
- Async work uses RxJava 1 schedulers (`applySchedulers()`/`applyIOSchedulers()`/`applyUISchedulers()` helpers on `BasePresenter`), not coroutines/Flow.
- Screen-to-screen navigation is abstracted behind the `Navigator` interface (`ui/navigator/Navigator.java`), implemented by `ELNavigator`. The app's presenters navigate via the `navigator` extension (`ui/navigator/PresenterNavigator.kt`), never by constructing `Intent`s directly; a feature module's presenters go through their feature's dependencies.
- `ui/activities`, `ui/fragments`, `ui/adapters`, `ui/bottomsheets`, `ui/dialog` (`AppDialogs`, the app's own pickers and inputs), `ui/views` are organized by feature area under `home/` (e.g. `home/workout`, `home/plan`, `home/routine`, `home/exercise`, `home/statistics` via fragments, `home/pro` for paid features).

### Data layer: Firestore-backed stores, not a local DB

- `ELDocumentStore` and `ELCollectionStore` (`common:data`, package `store`) are generic base classes wrapping Firebase Firestore `Query`/`CollectionReference`. They handle cache-then-live snapshot listening (`Source.CACHE` first, then `addSnapshotListener`), mutex-guarded single in-flight loads, and CRUD (`create`/`delete`) that no-ops during Firebase Test Lab runs (`CommonData.dependencies.isTestLabRun()`, which the app answers with `DeviceUtils.isFirebaseTestLabRun()`).
- Concrete stores under `data/datastores/{exercises,history,plans,routines,events}` subclass these and emit domain-specific EventBus events (subclasses of the events in `common:data`'s `store.events`) rather than using callbacks/RxJava for downstream consumers — presenters subscribe via `@Subscribe` methods.
- The Firestore-mapped models live in modules: the shared core (`ELFirestoreModel` base, `ELRoutine`, and the exercise, set and workout models) in `common:data`, and each feature's own in its `data` module (`ELUser`, `ELDevice` and `ELConsent` in `auth:data`, the plan models in `plan:data`, the Pro models in `pro:data`, `ELIntegration` in `settings:data`, the exercise library and picker in `exercise:data`), each under a `model` package.
- **Anything Firestore or Gson maps by reflection lives in its module's `model` package** (DTOs included, e.g. `exercise:data`'s `model/library/ExerciseLibraryDtos.kt`), which the module keeps with its own `consumer-rules.pro` (`-keep class com.everlog.android.<module>.model.** { *; }`). The app's `proguard-rules.pro` still keeps `config/` for Remote Config's JSON. R8 renames classes anywhere else in release builds, and `toObject` then fails with "No properties to serialize found". Debug builds aren't minified, so this only shows on nightlies and releases (2.18.0's picker broke this way). Check with `./gradlew :android:app:minifyReleaseWithR8` and `android/app/build/outputs/mapping/release/mapping.txt`.
- **New screens read through `common:datasync`** (`DataSync`, see its `README.md`; the app's instance is `AppDataSync`), not the stores: always the cache, synced with the server when a read needs it, with cache-only listeners for live updates instead of EventBus. It's replacing the stores screen by screen (TAS-462).
- `data/migration` implements a lightweight schema-migration system: `DataMigrationManager` tracks a `SCHEMA_VERSION` preference and runs numbered `Migration` implementations (`Migration1`, ...) sequentially against Firestore via `FirestorePathManager` — add new migrations here rather than mutating data ad hoc.

### Exercise library

The global exercise library is data in Firestore, not code: exercises in `global/exercises/all` and a registry of the ids they use (muscles, equipment, set-ups, grips, families, each with a display name) in `global/exercises/registry/current`. Firestore is the source of truth for both, in dev and prod separately.
- **Change them only with the tools in `tools/exercises/`**: `import.py` adds exercises from the licensed Exercise Animatic pack (propose, review, apply), `push.py` makes any other change (export, edit, dry run, then `--write`); dev first, never in the Firebase console. `tools/exercises/README.md` is the reference for the model, the rules and the routine; `schema.py` checks them on every push.
- **uuids never change**: routines, workouts and the onboarding's starter routines (`StarterExercises.kt`, uuids only) point at them, and the app shows the library's current name and image for each (`ELRoutineDecorator`). A rename shows everywhere, past workouts included.
- **Never delete or overwrite exercise images in Storage**: app versions before 2.10.0 show the copies stored in routines and workouts, which point at the images they had when saved. Each environment's exercises use that environment's own bucket.
- `ELExercise` doesn't read the newer fields (family, muscles, equipment and so on). The exercise picker (`exercise:feature`, package `picker`, for browsing from Home and picking for templates and workouts) reads them as `LibraryExercise`s with the registry, through `LoadExerciseLibraryUseCase` (`exercise:data`, with `ExerciseRepository`, the exercise stores and the guide use case), and hands picks on as `ELExercise`s.
- The exercise detail's Info tab (`ui/fragments/home/exercise/info`, behind Remote Config `exercise_details_v2`, which is meant to cover the whole detail screen as it moves to Compose) shows the library's `instructions` and `tips` through `LoadExerciseGuideUseCase`. While the flag is off it's `LegacyExerciseInfoFragment`, the image only.

### Managers layer (`managers/`)

Singleton-style managers encapsulate cross-cutting concerns and are the integration point for most external services: `auth/AuthManager` (Firebase Auth) + `LocalUserManager` (`auth:data`, the local session), `billing/BillingManager` + `BillingBridge` (Play Billing / Pro subscriptions), `analytics/AnalyticsManager` (routes to `FirebaseAnalytic` implementations of the `Analytic` interface), `firebase/FirestorePathManager` (the signed-in user's paths, on top of `FirestorePaths` in `common:firebase`; code in modules takes the user id and uses `FirestorePaths`) + `FirebaseStorageManager`, `integrations/GoogleFitIntegrationManager`, `api/ApiManager` (Retrofit-based REST, e.g. cover images), `RemoteConfigManager` (Firebase Remote Config), `appupdate/AppUpdateController` (Play In-App Updates), `PreferencesManager` (`common:persistence`) and `SettingsManager` (`settings:data`). `AppConfig` (`config/AppConfig.kt`) is the single object wiring together tunable constants (rest timers, plan limits, rating-prompt thresholds) and app boot sequencing (`configureApp()` called from `ELApplication.onCreate()`).

### Compose screens and the design system

New screens are built in Compose: a `CommonComposeActivity` (`common:compose`: wraps the content in `Theme`, closes when `requiredExtras` are missing), or the app's `SignedInComposeActivity` for screens with the user's data, which also closes without a signed-in user, a `CommonViewModel` (`common:mvvm`) with a `StateFlow` state, and coroutine use cases returning a `Flow<Load<T>>` for Firestore data (through `DataSync`) or Arrow `Either` for one-off work. The existing XML/MVP screens are unchanged. The design system lives in `common:compose` (`com.everlog.android.common.compose`), with its resources in `common:design`: `theme/` (colours, typography, shapes, spacing, read through `Theme`) and `elements/` (`AppScreen`, `AppBar` and `AppBarHeader`, `AppSurface`, `AppListGroup`/`AppGroupedList`, `AppListItem`/`AppListRow`, `AppFooter`, the buttons, `AppDialog` and so on). Its showcase (`showcase:feature`, debug builds only, Settings › Developer) has a page per element type. XML screens have a few twins of its elements so the two look the same, e.g. `ui/views/FloatingFooterView` for `AppFooter`: change both together.

- **Use the design system first.** Build screens from its elements and `Theme` tokens, never hardcoded colours, text sizes or dp values that a token covers. Lay content out the way its elements do: the 16dp screen margin, rows inside a group joined with dividers, groups 16dp apart, the same as the side margin (`AppGroupedList`).
- **Design mockups may predate it.** The Claude Design canvases (e.g. Everlog Onboarding) don't always follow the design system. Map each mockup piece onto an element and its spacing, and keep the standard styles over mockup-only sizes, colours or densities.
- **Flag anything that isn't in the design system.** When a screen needs something the design system doesn't have, say so (in the reply and the PR) and ask whether it should become a design system element or stay local to the feature, rather than deciding silently. Only skip the question when the answer is obvious: a generic group, card, row or button belongs in the design system, while something tied to one screen's behaviour (e.g. onboarding's animated question blocks) stays local. Local pieces live in the feature's package, with their sizes in a private object.
- **Design system changes ship separately** from the feature using them, in their own commits or PR, with a showcase example for anything new.
- **Shared components belong to the design system**, which moves to `common:compose`: a piece several screens use gets its own UI model, a showcase page, and goes in with the other elements, rather than into a module of its own. `ui/components/reorder` and `ui/components/rest` are already generic. `ui/components/exercisetable` (the exercise table, typing into its cells, the edit list), shared by the workout screen and the template editor, still uses the workout session model (`WorkoutBlock`, `WorkoutSet`, `SetRef`, `ValueField`), `ELExercise`, the weight unit and formatters: it stays in the app until it has its own row and cell model that the workout and template map onto.

### Background work

`services/workout/WorkoutService` + `WorkoutNotificationBuilder` run the active-workout foreground service/notification. `services/fcm/ELFirebaseMessagingService` handles push notifications. `receivers/` holds broadcast receivers.

## Code quality

The owner can't review every line of larger features (e.g. the Compose workout screen, TAS-455), so the code has to stand on its own: testable, easy to read and following good design, without needing the author to explain it.
- **Testable.** Keep logic out of composables and Android classes: rules in plain functions or classes (like `data/controllers/workoutsession`), screen behaviour in the view-model. Pass dependencies in through small interfaces (store, settings, analytics) and take `now` or a clock as a parameter, rather than reading singletons (`SettingsManager.manager`, `AnalyticsManager.manager`, `WorkoutManager.manager`) from inside a view-model, reducer or composable. Composables render state and forward events: they don't log analytics or open other screens themselves. Screen views go through the view-model's analytics interface (an `onResume` event), and other screens open through lambdas the activity passes to the screen.
- **Readable.** One responsibility per file, named after what it holds (screen, view-model, models, services, table, dialogs), and files small enough to read in one go: split a view-model that grows past a few hundred lines by concern. Names from the domain (set, round, block, rest) and small functions.
- **Clear code over comments.** Let names and structure say what code does. Comment only what the code can't say: why a choice was made, an edge case, a platform quirk. No comments that restate the line below, section markers, or doc comments on self-explanatory functions and parameters. No comments that compare with code that will go away ("as on the old screen") or name a stage, PR or ticket: they go stale. State the rule itself instead.
- **Consistent.** Follow the patterns already in the codebase (view-model and `StateFlow` state, design system elements, use-case style services) before inventing new ones, and say so when a new pattern is needed. A Compose screen loads data through repositories and use cases in the features' `data` modules (e.g. `ExerciseRepository` in `exercise:data`, `RoutineRepository` in `template:data`, `WorkoutRepository` in `workout:data`): a `Flow<Load<T>>` for Firestore data read through `DataSync` (e.g. `LoadExerciseGuideUseCase`), Arrow `Either` for one-off work (e.g. `BuildStarterRoutinesUseCase`), not through interfaces of its own in the UI package or try/catch in the view-model.
- **Ask before it grows.** When doing it properly needs a change beyond the PR's scope (a refactor of existing code, a new dependency, a design system change, moving logic around after the fact), say what and why and wait for a go, rather than folding it in.
- **Review before handing over.** Re-read the whole diff against these points before asking for a review or merge, and list what was checked and what was left.

## User-facing copy

Anything users read (in-app strings, release notes, the store listing, ads, notifications, emails) follows the tone of voice guide in the "Tone of voice" section of the [Product market fit](https://app.notion.com/p/3e8662113da880779b9be047669d1502) page in Notion: its principles, words to use and avoid, rules for each place, and examples. Read it before drafting copy. In short: plain, direct and concrete, in the words lifters use; every claim true today (no superlatives, "#1", "free forever", or AI and coaching we don't have); calm and a little dry, without hype or exclamation marks; British English and sentence case. Release notes are one friendly paragraph under Play's 500 characters about the features people will notice (not small UI polish), with emoji only where they help, not on every point.

## Branches and pull requests

- Prefix branch names with the equivalent Notion ticket's ID, if available, e.g. `tas-123-something-changed` (no brackets — git doesn't allow them in branch names).
- Prefix PR titles with the Notion ticket ID in brackets, if available, e.g. `[TAS-123] Something changed`.
- Individual commits within a PR don't need the ticket prefix. Instead, each commit message should briefly summarise what changed in that commit, so the work can be picked back up later with quick context.

Every PR that changes app behaviour is tried on an emulator before it's handed over, when the change can be reached there: install the debug build, go through what changed (including the cases the change hides or guards, e.g. a missing Remote Config value), and say in "How is this change tested?" what was checked on which emulator and what couldn't be. Unit and instrumented tests don't replace this. Build-only, docs or tooling changes skip it.

Use `PULL_REQUEST_TEMPLATE.md` for PR descriptions (`## What does this pull request change?`, `## Demo`, `## Screenshots`, `## How is this change tested?`). Irrelevant sections (e.g. Demo/Screenshots for a non-UI change) can be dropped.

Merging a PR:
- Before merging, review the entire diff (`gh pr diff <n>`) the way a reviewer would, not just the files you remember changing. Look for bugs, for edge cases nobody has raised yet (offline or a weak signal, missing or malformed data, no signed-in user, process death, older app versions reading newer data, cost of Firestore reads) and for anything missing (tests, docs, strings, the Notion ticket). Fix what you can in the PR and say what you changed. Stop and ask about anything unexpected, anything you can't resolve yourself, or an edge case so unlikely that fixing it is a judgement call.
- Merge only once all checks pass, never while one is pending or failing.
- Always squash merge, without a commit description: `gh pr merge <n> --squash --admin --body "" --delete-branch`. `master` requires a review the solo repo never gets, so the admin override is expected.
- Afterwards clean up local git: switch to `master`, pull, and delete the merged local branch.

## Testing

Coverage is still small, so check the actual classes before assuming conventions:
- Unit tests (`android/app/src/test/java`) are plain JVM JUnit 4 tests written in Kotlin with Truth assertions and backtick test names — see `config/HomeNotificationTest`, `data/controllers/workoutprefill/WorkoutPrefillControllerTest` and `data/controllers/statistics/ExerciseStatsControllerTest` as models. There's no Robolectric or mocking library. Generic test helpers and the test libraries live in `common:test` (e.g. `FakeCoroutineDispatcher`), fixtures for the shared models in `common:data-test` (e.g. `WorkoutFixtures.kt` for building workouts and sets), and fakes of a feature's data in its `test-fixtures` module (e.g. `FakeExerciseRepository`, `FakeRoutineRepository`), and fixtures built on the app's other models in its `testutil/`.
- View-models are unit tested with small fakes of their interfaces (store, settings, analytics), `FakeCoroutineDispatcher` (`common:test`) and a pinned clock — see `ui/activities/workoutlog/WorkoutLogViewModelTest`.
- A Compose screen's tests cover three levels: its main features (the journeys people take every time), medium-importance features (options, editing, less common paths) and edge cases (missing data, things arriving late, values at their limits, process death). Unit tests cover all three for the view-model, rules and formatting; instrumented tests cover the main journeys and the ways out of the screen (finishing, discarding), plus one end-to-end test through the real activity for its wiring (launching, permissions, results from other screens, where it goes on exit).
- Instrumented tests (`android/app/src/androidTest/java`): `LoginActivityTest`, an E2E test that drives a real login using the `E2E_TEST_USER_EMAIL`/`PASSWORD` secrets against a real Firebase project, `WorkoutNotificationBuilderTest`, Compose scenario tests (`WorkoutLogScenarioTest`, `ExercisePickerScenarioTest` in `exercise:feature`, run with `./gradlew :android:exercise:feature:connectedDebugAndroidTest`, `OnboardingScenarioTest`), and end-to-end activity tests (`WorkoutLogActivityTest`, `ExercisePickerActivityTest`, `OnboardingActivityTest`). An end-to-end test runs a screen through its real activity, signed in with the E2E account (`testutil/E2EAccount`) so Firestore works, and deletes anything it saves. Other screens' launches are intercepted with `Instrumentation.ActivityMonitor`, which can also answer with a result. With `ActivityScenario.launchActivityForResult`, wait for the activity to be destroyed before reading its result. A scenario test (e.g. `WorkoutLogScenarioTest`) drives a whole screen as a user would, with its real view-model, through a few high level journeys rather than a test per detail, as each is slow: the view-model's unit tests cover the details. Find nodes by test tags (`WorkoutLogTags`, and `ExerciseTableTags` for the table and edit list) where text repeats. When a screen gains a key interaction, extend its scenario rather than adding tests. **Every change to how the new workout screen (TAS-455) behaves comes with tests in the same PR:** its scenario test (`WorkoutLogScenarioTest`) covers the interaction end to end, through the UI or, for the notification's buttons, the broadcasts `WorkoutService` sends, and the view-model's unit tests cover its rules wherever they can. Run one class on an emulator with `./gradlew :android:app:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=<class>`.

Gotchas when unit testing app code on the JVM:
- `SettingsManager`/`PreferencesManager` read `SharedPreferences` through `AppContext` (`common:kotlin`), which isn't set in unit tests. This is hit indirectly by a lot of model code (e.g. every `ELSet.getWeight()` reads the weight unit). Call `InMemorySharedPreferences.install()` (the class is in `common:test`, the `install`/`uninstall` helpers in `settings:test-fixtures`) in `@Before` and `uninstall()` in `@After`, then set settings through `SettingsManager.manager`.
- ThreeTenABP (`org.threeten.bp`) has no time-zone data outside Android, so unit tests also depend on the plain JVM `threetenbp` (added to every module's unit tests by the base convention plugin), which includes it. Without it, anything using `ZoneId.systemDefault()` (e.g. `ELWorkout.inRange()`, the `Date` extensions in `utils/DateExt.kt`) throws `ZoneRulesException`.
- Code that reads the current time (`Date()`, `System.currentTimeMillis()`) should take `now` as a parameter so tests can pin it — see `WorkoutPrefillController.prefill`.

Testing alarms on an emulator (e.g. the app usage reminder in `AppUsageReminderManager`): list pending ones with `adb shell dumpsys alarm` (the app's entries are tagged with the receiver name), and make them fire by moving the clock instead of waiting — `adb shell settings put global auto_time 0`, then `adb shell cmd alarm set-time <epoch millis>` (no root needed). Jump past the end of an alarm's `window` to force an inexact alarm to be delivered. Switch `auto_time` back to `1` afterwards. App updates keep existing alarms; a force-stop or reboot clears them.

More emulator testing notes (debug package is `com.everlog.dev`):
- Timber has no logcat tree, app logs go to Hyperlog and Crashlytics. Read them with `adb exec-out run-as com.everlog.dev cat databases/com.hypertrack.common.device_logs.db > logs.db`, then `sqlite3 logs.db "select device_log from device_logs order by _id desc limit 20"` on the host (the emulator has no `sqlite3`).
- A force-stopped app is in Android's stopped state and gets no broadcasts (e.g. `MY_PACKAGE_REPLACED` on `adb install -r`) until it's opened again. On Android 15+ it gets `BOOT_COMPLETED` when that happens.
- To try Remote Config values without the console, edit the cached copy in the `REMOTE_CONFIG` string in `shared_prefs/EverlogPreferences.xml` (`run-as com.everlog.dev cat`/`sh -c 'cat > ...'`) while the process is dead (`adb shell am kill com.everlog.dev`, which keeps alarms, unlike `am force-stop`). The app rebuilds it from Firebase's own cached values at launch, even offline, so an edit only survives in background paths (alarms, receivers). To see a different value on screen, change the parameter in dev Remote Config (the REST API with `tools/firebase/admin-credentials-dev.json`; debug builds fetch with no minimum interval), relaunch twice so the screen is built from the new copy, then put the value back.
- To test an upgrade from a released version, build its tag (`git switch --detach <tag>`, then `./gradlew :android:app:assembleDebug` and copy the APK out before switching back and rebuilding, as both write `app-debug.apk`; tags up to 2.21.2 build from `mobile/` instead, so copy `secrets.properties`, the keystores and `google-services.json` files into `mobile/` first and take `mobile/build/outputs/apk/debug/mobile-debug.apk` from `./gradlew :mobile:assembleDebug`), install it over the current one with `adb install -r -d` (downgrade, keeps data), use it, then `adb install -r` the new build.
- Turn off a single notification channel with `adb shell am start -a android.settings.CHANNEL_NOTIFICATION_SETTINGS --es android.provider.extra.APP_PACKAGE com.everlog.dev --es android.provider.extra.CHANNEL_ID <id>` and tap its toggle (`uiautomator dump` for the bounds). Check it with `dumpsys notification` (`mImportance=0`).
- The in-app rating prompt (`managers/apprate/RatePromptController`) never shows Play's dialog in debug builds, which use `FakeReviewManager`. Instead a toast says when it would have launched. To skip the qualifying actions, set `<int name="RATE_PROMPT_ACTIONS_SINCE_LAST" value="2" />` in `shared_prefs/EverlogPreferences.xml` (same steps as for Remote Config above), then finish a workout of 5+ minutes. To avoid waiting 5 minutes, start a workout, kill the app and move `createdDate` back in the `ONGOING_WORKOUT` JSON in the same file (the in-app timer follows it). Relaunch with a cleared task (`am start -f 0x10008000 -n .../SplashActivity`) and tap Resume, otherwise the restored workout screen writes its in-memory copy back over the edit. The workout's heads-up notification can cover the Finish button, so swipe it away first. The real dialog only appears in builds installed from Play: internal app sharing (Submit disabled) or the internal test track, with an account that hasn't reviewed the app.
- Get to the home screen without tapping through: `adb shell am start -n com.everlog.dev/com.everlog.ui.activities.splash.SplashActivity` (logged in), and leave it with `adb shell input keyevent KEYCODE_HOME`.
